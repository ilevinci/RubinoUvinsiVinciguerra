\subsubsection{System View}
The architectural approach we adopted for the BBP platform is a 4-tier architecture, which consists of the following layers:
\begin{itemize}
    \item \textbf{Presentation Layer}: this layer is responsible for the user interface and user experience. It includes a mobile application that allow users to interact with the platform while interacting with the internal storage of the mobile device to store the user's path inventory.
    \item \textbf{Gateway Layer}: this layer acts as an intermediary between the presentation layer and the application layer. It handles requests from the user interface and forwards them to the appropriate services in the application layer.
    \item \textbf{Application Layer}: this layer contains the core business logic of the platform.
    \item \textbf{Data Layer}: this layer is responsible for data storage and management. It includes databases that store user information, path data, and other relevant information.
\end{itemize}
As specified above, the application layer is divided into two sub-layers to separate the main application services that implement main functionalities of the application from the user management service that handles user authentication, authorization, and profile management.
When the Gateway Layer receives a request from the Presentation Layer, it forwards the request to the appropriate service in the Application Layer. The service processes the request and interacts with the Data Layer as needed to retrieve or store data. Once the service has completed its task, it sends a response back to the Gateway Layer, which then forwards the response to the Presentation Layer for display to the user.
Furthermore, our application strongly depends on external services, mainly to retrieve meteorological data and to process and display paths from raw sensor data. The communication protocol that is used in these scenarios are Rest API calls.
In an ideal implementation, our architecture would be geographically distributed, with multiple instances of each layer deployed in different regions to ensure high availability and low latency for users around the world.
The geographical distribution would also contribute to reduce latency when communicating with external services, as instances could be deployed closer to the external services' servers.

\subsubsection{Detailed View}
\textbf{Client Tier}: The client tier contains the mobile application that provides the UI for the BPP platform to users to allow them to interact with the platform. Through the UI, the users can
perform various actions that can be grouped into three main categories: account management, path insertion, and path research. The last category is the only one that is also available to non-registered users.
\begin{itemize}
    \item \textbf{Account Management}: this functionality allows users to create and manage their accounts on the platform. Users can register, log in, update their profile information, and change their searching area.
    \item \textbf{Path Insertion and Publication}: this functionality allows registered users to insert new bike paths into the platform. Users can either manually input path data or use the automated path data collection feature to record their bike rides using the mobile device's sensors.
    \item \textbf{Path Research}: this functionality allows users to search for bike paths that connect their desidered origin and destination points. When they exist, users can customize the visualization of the existing paths
    and they can select a path to view more detailed information about it.
\end{itemize}
While account management, path processing, publication and research require an internet connection, the path insertion functionality is partially available offline. This is due to the fact that we clearly distinguish between the concepts of "bike path" and "record": a record is a set of performance metrics and meteorological data
that is only available to the user that recorded it, while a bike path is a shared entity that is available to all users to the platform and it only contains the "publishable" data of the cycling sessions: the geographical reconstruction of the path, the status of its streets and the presence of obstacles.
Therefore, since a record is private, it is only stored locally on the user's device and it can be accessed offline. Its creation though does need an internet connection in order to interact with the external providers to retrieve meteorological data and to process raw sensor data into a human-readable and visualizable format.
The same concept applies to manually inserted paths that have not been published yet: we handle these drafts locally on the user's device until (and if ever) the user decides to publish them. \\
The presentation layer is therefore responsible both for providing the user interface and for managing the local storage of the user's path inventory.

\vspace{0.5cm}
\noindent \textbf{Gateway Tier}: The gateway tier acts as an intermediary between the presentation layer and the application layer. It receives requests from the mobile application and forwards them to the appropriate services in the application tier.
In particular, the gateway tier separates account management and permission related requests to a specific server, whereas all path related requests are forwarded to the application server.

\vspace{0.5cm}
\noindent \textbf{Application Tier}: The application tier contains the core logic of the BPP platform and it is responsible for processing both path publication and research requests. It also contains the authentication service that manages user accounts and permissions.
The application server in this tier is structured to be scalable and it could therefore be replicated and distributed geographically.

\vspace{0.5cm}
\noindent \textbf{Data Tier}: The data tier is responsible for storing and managing all the data used by the BPP platform. It contains two main databases: one for user account information and another for published bike paths.
Both databases are designed to be highly available and to provide eventual consistency across all replicas, ensuring that all users have access to the most up-to-date information.

\subsection{Component view}
This section gives a more detailed description of the components of the architecture of the BPP system.

\vspace{0.5cm}
\noindent\makebox[\textwidth][c]{\includegraphics[width=1.5\textwidth]{images/ComponentDiagram2.png}}

\vspace{0.5cm}
The main components of the system are:
\begin{itemize}
    \item \textbf{User Management Service}: This service is responsible for managing user accounts, including registration, authentication, and profile management. It ensures that only authorized users can access certain features of the application.
    \item \textbf{Automated Path Data Collection Service}: This service collects raw data from the mobile device's sensors during a cycling session. It gathers information such as GPS coordinates, speed, elevation, and other relevant metrics and stores them in the local storage of the device.
    \item \textbf{Path Data Transformation Service}: This service processes the raw sensor data collected during a cycling session and transforms it into a human-readable and visualizable format. AApart from reconstructing paths, it gives an evaluation of each street's conditions, and identifies obstacles along the route. It is also responsible for computing and storing performance metrics.
    \item \textbf{Meteorological Data Retrieval Service}: This service interacts with external meteorological data providers to retrieve weather information for the area where the cycling session took place. It ensures that the weather data is accurately associated with the corresponding record data.
    \item \textbf{Path Research Service}: This service allows users to search for bike paths that connect their desired origin and destination points. It retrieves relevant paths from the database and provides customization options for visualization.
    \item \textbf{Path Publication Service}: This service handles the publication of bike paths to the platform. It ensures that the path data is properly formatted and stored in the database, making it accessible to other users.
    \item \textbf{Manual Path Insertion Service}: This service allows users to manually input bike path data into the platform. It provides an interface for users to enter path details and ensures that the data is correctly formatted and stored.
    \item \textbf{Inventory Handling Service}: This service manages the local storage of the user's path inventory on the mobile device. It allows users to access and manage their records and drafts offline.
\end{itemize}

\subsection{Deployment view}
This chapter describes the deployment view of the BPP system. it outlines the execution
environment of the system and details the gegraphical distribution of the hardware components that host the
software making up the application.

\vspace{0.5cm}
\noindent\makebox[\textwidth][c]{\includegraphics[width=1.3\textwidth]{images/Deployment_Diagram.drawio.png}}

\noindent The deployment architecture follows a Four-Tier approach.
\begin{itemize}
    \item \textbf{The first tier} is a Thick Client able to provide parts of the functionalities (gathering of information and offline storage) also when it is not connected to the Server.
    \item \textbf{The second tier} consists of the Gateway and the Load balancer. The Gateway exposes the public endpoint and route the requests toward the correct type of service (Account Server or Application Server). This layer works also as shield against external treats. The communication between first and second tier takes place via HTTPS protocol.
    \item \textbf{The third tier} consist of two types of servers: The ones to manage all the things regarding the personal account of a user and the ones that regard the "shared" part of the application, i.e. the publication of bike paths. This separation between the two aspect allow to easily achieve independent scalability of the two type of service, and allow the system to avoid the congestion of both service if only one is managing a big quantity of requests. In other words this kind of separation introduces a high level of decoupling.
    \item \textbf{The fourth and last tier} is dedicated to the Data, the databases do not communicate directly with internet but only with the Servers responsible to manage the information. The communication between these tiers takes place via TCP/IP protocol.
\end{itemize}

We proceed to provide further details about the elements in the graph.

\begin{itemize}
    \item \textbf{Database Server for Published Paths} \\
    This database stores all the published paths by registered users.
    The system shall be highly available and shall be able to provide eventual consistency across all the
    replicas, so all the set of available paths will be visible to all the users around the world.
    \item \textbf{Database Server for Registered Users} \\
    This Database stores all the personal information of registered users such as name, e-mail and the hashed password.
    \item \textbf{Application Server}\\
    This Server is responsible to process all the requests regarding the publication and the search of bike path from the final user.
    This component manipulates data, and then it has direct access to the related Database.
    \item \textbf{Account Server}\\
    This Server is responsible to manage all the request that regard the accounts of the end user and the related information.
    This component manipulates personal data of the users, and then it has access to the related Database.
    \item \textbf{Load Balancer} \\
    It distributes incoming requests across multiple Gateway to optimize system performances and avoid to overloading one server.
    \item \textbf{Firewall}\\ %Ops... non ci sono nel deployment diagram <-- Sistema
    Monitors incoming network traffic, blocking potentially harmful packets before they reach the system. Positioned before the load balancers it creates
    a safe perimeter around the network.
    \item \textbf{Mobile Device} \\
    This represents the device used by the end user. It requires the app installed in order to access the BPP application. 
\end{itemize}
\subsection{Runtime view}
In this section, we describe the dynamic behavior of the BBP system by detailing the flow of messages between the architectural components. 
We utilize Sequence Diagrams to model the interactions required to fulfill the primary Use Cases.

To ensure the diagrams remain readable and focused on the core logical flows, we applied the following abstractions:

\begin{itemize}
    \item \textbf{Authorization Checks:} For the sake of simplicity, we have omitted the repetitive verification steps where the system ensures a request is authorized. 
It is implicitly assumed that the User Management Service and the Gateway enforce security policies (e.g., ensuring that a user can only view or modify 
their own private sessions and cannot alter data belonging to other users).

\item \textbf{Error Handling:} We have excluded low-level error handling related to incorrectly specified parameters, network timeouts, or minor validation issues, unless 
they are significant to the specific use case (e.g., login failure).

\item \textbf{Caching and Optimization:} While components such as the Load Balancer or API Gateway may implement caching mechanisms to reduce latency and database load, 
our diagrams represent the general case where requests are processed by the application servers and reach the persistence layer.
\end{itemize}

These abstractions allow us to focus on the main architectural interactions and the data flow necessary to execute the functional requirements.

%PRIMO SEQUENCE DIAGRAM

This diagram depicts the registration process initiated by the Unregistered User. Upon submitting personal data via the Mobile Application, the request is forwarded to the UserManagement component.

The system first queries the UserDBMS to verify that the email or nickname is not already in use.

If the user exists: The flow terminates with an exception, and an error message is displayed to the user.

If the data is new: The UserManagement component hashes the password and persists the new profile in the database. Finally, it returns a confirmation to the Mobile Application, which saves 
the user's session locally to complete the process.


%SECODOND SEQUENCE DIAGRAM

This diagram illustrates the authentication flow initiated by a Registered User. After the user enters their credentials, the Mobile Application forwards the authentication request to the UserManagement component.

The system verifies the user's identity by hashing the provided password and querying the UserDBMS for a match.

If the data is incorrect: The database returns no result, causing the system to raise an exception and display an "Invalid credentials" error to the user.

If the data is correct: The UserManagement component updates the user's login history in the database and generates a secure session token (AuthToken). This token is returned to the Mobile Application, 
which stores it locally to maintain the authenticated session.

%TERZO SEQUENCE DIAGRAM
This diagram details the automated tracking process handled by the Mobile Application and its internal component, the Automated Path Data Collector (APDC).

Once the user initiates the ride, the APDC creates a local session and continuously records sensor data (GPS, Gyroscope, Accelerometer). The acquisition loop terminates either through a manual user action or 
automatically if the system detects prolonged inactivity.

Following the stop event, the APDC performs parallel requests to the MeteoServiceProvider for weather conditions and the MapServiceProvider for map matching. The consolidated data is presented 
as a preview to the user. Finally, after any necessary manual corrections, the user decides to either save the session to local storage or discard the data entirely.

%FOURTH SEQUENCE DIAGRAM
This diagram portrays the workflow for manually constructing a bike path, managed by the Mobile Application and the Manual Path Insertion Module (MPIM).

The process centers on an iterative loop where the user inputs details for individual street segments. For each segment, the MPIM validates the location against the MapServiceProvider and verifies geographical continuity with the previously added segment.

If valid: The segment is temporarily stored, and the user receives confirmation.

If invalid: An error message is returned.

Once all segments are entered, the system generates a final path preview. The user then concludes the process by either saving the path to local storage or discarding the session.

%FIFTH SEQUENCE DIAGRAM
This diagram depicts the retrieval and visualization of a specific past ride. The process relies on the Inventory Handling component to access the device's local storage.

Upon accessing the log view, the Mobile Application requests the list of saved sessions from the Inventory Handling component, which scans the local file system and returns the available records.

Selection and Rendering: When the user selects a specific session, the application retrieves the full raw data (metrics and coordinates) from the local JSON/XML files.

Map Integration: To provide visual context, the Mobile Application iteratively requests map tiles or vector data from the external MapServiceProvider corresponding to the recorded coordinates. Finally, it combines the local path data with the external map background to render the complete session details.

%SIXTH SEQUENCE DIAGRAM
This diagram illustrates the search workflow managed by the Mobile Application and the backend PathSearchEngine.

The process begins with the definition of the trip's origin: the user may either select the automatically detected GPS position or manually input an address. In the case of manual input (and for the subsequent destination entry), the application invokes the MapServiceProvider to convert the addresses into geographical coordinates.

Once the origin and destination coordinates are established, the Mobile Application queries the PathSearchEngine. This component accesses the BikePath DBMS to retrieve paths that match the specified proximity criteria, ranked by their quality score, and returns the result list to the user.

%SEVENTH SEQUENCE DIAGRAM
This diagram illustrates the visualization of a specific bike path selected from the search results.

It is explicitly assumed that the Mobile Application has locally cached the list of paths retrieved during the previous Search phase (UC6). Consequently, the application retrieves the specific path data directly from its local memory, eliminating the need to query the PathSearchEngine or the backend database again for this step.

The only external communication required is with the MapServiceProvider: the application iteratively requests the necessary map tiles (or vector data) corresponding to the cached street coordinates. The final view is rendered by overlaying the local path data onto these retrieved map tiles.

%EIGHTH SEQUENCE DIAGRAM
This diagram depicts the process of transforming a private local record into a shared public path.

Initially, the Mobile Application retrieves the specific session data from the local Inventory Handling component to display a final preview to the user. Upon user confirmation, the data is transmitted to the backend PathPublication component.

The system first persists the new path in the BikePath DBMS. Subsequently, it executes the critical merging logic: the component iterates through every street segment contained in the path, fetches the existing aggregate data for that specific location, recalculates the street's status 
based on the new input, and updates the global database. This ensures that the public map reflects the combined inputs of the community.

\subsection{Selected architectural styles and patterns}

\textbf{Client Server 4-tier Architecture}\newline

\noindent The system adopts a 4-Tier Infrastructure. With this solution we can split the
layer that manage the application and communicate with the Databases from the Gateway layer
that hide all the application logic and acts as single entry point for all client requests.
With this solution the system expose only a secure, monitored endpoint to the external network.
The separation allows also the internal architecture to evolve or scale without impacting the client. \newline

\noindent\textbf{Service-Based Architecture}\newline

\noindent The application is decomposed into two independent Service: The Account Manager Service and the Path Manager Service.
The first Service is responsible to all the operations that regard the creation, modification and deletion of accounts.
The second Service is responsible to all that operation that regard the publication and the search of bike paths. This 
Separation of Concerns (both logical and physical) offers significant advantages:
\begin{itemize}
    \item Independent scalability: The two services can be scaled separately from one another.
    \item Fault Isolation: Fault that affect one service do not affect the other.
    \item Separation of Responsibilities: Each Service manages its own dedicated database schema, assuring decoupling. 
\end{itemize} 
\noindent
\textbf{Bulkhead Pattern} \newline

\noindent The adoption of a Service-Based Architecture enables this pattern, responsible to ensure system resilience and graceful degradation.
The pattern is implemented via the physical and logical separation of Account Manager Service and the Path Manager Service.
These two services use separate servers and use different databases.\newpage

\noindent\textbf{Command Pattern - CQRS} \newline

\noindent The system exploits the Command Pattern to decouple the actions requested to the system
by a user and the implementation of that action in the server-side of the application.
Since all the possible operations concerns either the publication of a path or the search for a path we can
laverage CQRS (Command Query Responsibility Segregation) to split the "Command" part from the "Query" part.
The "write side" (command model) handles all the operations that regard the publication of paths prioritizing the consistency and rule validation for each published path while the 
"read side"(Query model) handles all the search operations. This query model will retrieve the pre-calculated bike path, ensuring quick response time
due to the bypass of all complex domain logic.\newline

\noindent\textbf{Observer Pattern} \newline

\noindent The Observer pattern is used to manage the interaction between GPS and accelerometer and the user device.
GPS and accelerometer are the 'Subject' and the ClientManager is the 'Observer'.

\subsection{Other design decisions}
\textbf{Session Token}\newline\newline
Each time a user logs into the system, this provides the user with a TokenID that 
remains valid for a set about of time. When a user is not registered or logged into the system they have not this token.
Without is not possible to interact with the remote part of the application that manages the path (Path Manager Service) to publish a 
Path and cannot record personal Cycling Session, i.e. the user must be logged into the System to use these features. Without the token a user
can only search for published bike path.\newline\newline
\textbf{Consistency Model}\newline\newline
This regard the implementation of the Databases. The system adopts Linearizability for the account's databases, with this consistency model 
each operation related to accounts appears to take effect instantaneously at some point between its invocation and its competition. With this approach
even if we have multiple copies of the Database the system behaves as if there were only a single copy of the data, so the system ensure that once a write is acknowledged by the system, all
the future read operations (e.g. logins) will reflect that change, preventing race conditions that could lead to a bad user experience.\newline For the Bike paths' databases the system adopts an eventual consistent model prioritizing hight 
availability and low-latency than consistency. So, when a new path is published, the write is propagate asynchronously to all the other replica. When a user
publishes a path this is written on the closest copy of the database, all the replicas eventually converge to the same state.\newline\newline
\textbf{Data Portability and Storage Strategy}\newline\newline
Unlike public paths, personal records (including traveled path) are not stored on the system's database but are kept exclusively on the user's device storage.
This strategy reduces the overall cost of the infrastructure. To ensure that the user does not lose data if he uninstalls the application the system support data export and import using
GPX (GPS Exchange Format). We selected format is the standard for sharing GPS data and ensure that user can export personal rides and visualize them also on
third party software or migrate them to a new device.\newline\newline This approach also reduces the impact of an eventual data breach.\newline\newline
