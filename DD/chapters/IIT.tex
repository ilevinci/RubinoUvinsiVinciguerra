\section{IMPLEMENTATION, INTEGRATION AND TESTING}

\subsection{Overview}
This chapter explains in details how the BBP system will be implemented and tested.
\subsection{Implementation Plan}
Since the BBP system is logically and physically separated into two distinct parts (online and offline functionalities) the two sub-system will be implemented independently of each other.
\newline\newline
In order to facilitate rapid prototyping of core services, the token system that is used to give registered and logged users access to the reserved functionalities, will be initially stubbed. The logic will instead be implemented during the final integration phase.
\begin{itemize}
    \item \textbf{Offline Functionalities}\\
    In order to implement offline functionalities, this
    part of the system, which is located in the Client tier, will be implemented by
    following a Thread-Based Strategy. Since the view of the local inventory 
    and the export/import of local data depend on the existence of data, the implementation order
    of the various functionalities will be dictated by the following data lifecycle:\newline\newline Insertion $\to$ Visualization $\to$ Management\newline\newline
    At the implementation level, this implies that the order of development will be the following: first the functionalities related to path creation and deletion will be implemented, then those related
    to path visualization and finally the ones to perform the export and import of records.
    \item \textbf{Online Functionalities}
    The Server-side of the application will also be implemented by following a Thread-Based strategy.\newline
    Since the online functionalities consist of two services (Account Manager Service and Path Manager Service) they can be
    implemented independently of each other. Two separate teams can work in parallel, one for the Account Management side and the
    other team for the Path Management side.
\end{itemize}

\subsection{Component Integration and Testing}
In this section, we will present the testing plan, which will follow the subsequent approach:
the offline functionalities will be the first to be tested by using stubs when needed.\newline\newline
\noindent Online functionalities will be tested via drivers that represent a user to avoid the complexity introduced by the network, at least for the initial phases of testing.\newline\newline Once both sections are individually tested, a full integration test (also considering the network) will be performed.

\subsubsection{Testing Offline Functionalities}
The following functionalities all require an active user session, i.e. a valid token.
Nevertheless, in order to be coherent with what is said in the implementation plan, the testing phase will bypass the existent token verification mechanism, at least for the initial phases of testing.\newline\newline
\textbf{Manual Path Insertion}

\vspace{0.5cm}
\noindent\makebox[\textwidth][c]{\includegraphics[width=0.5\textwidth]{images/Testing1.png}}

\vspace{0.5cm}
\noindent The tested feature include all the operation that let a user manually build a path by inserting the
individual streets by hand. The test aims to verify the coherence of the inserted path. It verifies aspects such as:
\begin{itemize}
    \item Rejecting street types tagged as unsuitable for bicycles (e.g., highways, pedestrian-only zones).
    \item Enforcing graph connectivity, preventing the insertion of a segment that is not physically connected to the previous one.
    \item The upper bound for number of possible streets in one path, and also that the system correctly manages this scenario.
\end{itemize} 

\newpage
\noindent\textbf{Automatic Path Insertion}

\vspace{0.5cm}
\noindent\makebox[\textwidth][c]{\includegraphics[width=0.5\textwidth]{images/Testing2.png}}

\vspace{0.5cm}
\noindent The tested functionalities include all those regarding the automatic tracking of a path. 
The system is stimulated with the injection of coordinates and other sensor data
via stubs that simulates the real hardware systems that are used to automatically track a path.
The test verifies aspects such as:
\begin{itemize}
    \item The quantity of errors registered during the tracking does not significantly affect the registered path (less than 3 errors per kilometer). What we define as error is: the detection of an obstacle that do not exist, the detection of a wrong street, incorrect values regarding speed exceeding 5 km/h.
    \item The system reaction to the injection of completely wrong values such as: discontinuous coordinates, impossible values for elevation gain, average speed and other metrics.
\end{itemize}

\vspace{0.5cm}
\noindent\textbf{Path Visualization}

\vspace{0.5cm}
\noindent\makebox[\textwidth][c]{\includegraphics[width=0.5\textwidth]{images/Testing3.png}}

\vspace{0.5cm}
\noindent The tested functionalities regard the ability to search and visualize local records and the specific tests aim to verify the correctness and soundness of the interaction
between the system end the internal file system of the user's device.

\noindent\textbf{Path exportation and Importation}
\newline\newline
This test validates the system's ability to serialize internal records into the
standard GPX format and, vice versa, to parse external GPX files into valid local records.
The test verifies that:
\begin{itemize}
    \item The file is syntactically correct and it can be also opened by third-party tools.
    \item All the internal attributes of a record (distance, speed, time) are correctly mapped and reported into the file.
    \item The system is resilient when stimulated with invalid or very large files.
\end{itemize}

\vspace{0.5cm}
\noindent\makebox[\textwidth][c]{\includegraphics[width=0.7\textwidth]{images/Testing4.png}}

\vspace{0.5cm}
\noindent This test aims to observe the interaction between the application logic

\noindent\textbf{Path Merging}\newline\newline

\vspace{0.5cm}
\noindent\makebox[\textwidth][c]{\includegraphics[width=0.7\textwidth]{images/Testing5e.png}}

\vspace{0.5cm}
\noindent This test verifies that the merge mechanism works as intended in order to
correctly update data related to streets and their status. The test aims to verify that:
\begin{itemize}
    \item Given a path P the Server is able to retrieve all the information about the roads that compose it from the database.
    \item For each road R in P, either the existent information is updated on the database or a new tuple is created (if the street has never been inserted).
    \item The overall score of the path is correctly computed according to the result of the merging.
\end{itemize}

\subsection{Additional Specifications on Testing}
For every test suit that requires a database, a lightweight, disposable docker container which also runs the exact database engine that will be used in production will be used. After each test, the container is destroyed in order to ensure a clean state for future testing.
\newline\newline
This approach is extended with container orchestration to simulate a scenario with multiple replica in order to verify the adopted consistency models.
